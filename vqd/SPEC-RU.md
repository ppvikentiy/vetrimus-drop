# Формат VQD, версия 1

VQD передаёт один файл с одного дисплея на одну камеру. Канал не имеет сетевого пути и подтверждения. Отправитель излучает повторяющуюся последовательность символов QR. Получатель может начать с произвольного кадра, может пропустить произвольный кадр и завершает приём, когда наблюдено достаточное множество различных символов.

Текст настоящего документа является нормативным, если не помечен как *пояснение*. Ключевые слова MUST, SHOULD и MAY толкуются в соответствии с RFC 2119.

Статус: черновик, версия 1. Эталонная реализация: `src/` в настоящем каталоге. Лицензия: Apache-2.0.

English edition: [SPEC.md](SPEC.md).

## 1. Построение

- Канал является односторонним. Кадры переносят фонтанные символы LT. Отдельный кадр не является обязательным. Потеря, повтор, перестановка и отложенное начало увеличивают только длительность передачи.
- Файл разбивается на **сегменты** не более чем из 4096 **блоков**. Целевое значение по умолчанию — 2048 блоков. Каждый сегмент кодируется, декодируется и проверяется независимо. Сегмент принимается только при равенстве его SHA-256 значению в манифесте.
- Версия 1 не определяет ни сжатия, ни шифрования. Бит 0 флагов манифеста зарезервирован для условия «сегменты сжаты gzip». Отправители MUST записывать флаги `0`. Получатели MUST отклонять всякое иное значение.
- Отрисовка символа QR находится вне области применения настоящей спецификации. Кадр является непрозрачной байтовой строкой. Значение 2953 есть ёмкость QR версии 40, коррекция ошибок L, байтовый режим. Размер кадра допустим, когда получаемая длина блока лежит в замкнутом интервале от 16 до 65535 байт.

Многобайтовые целые имеют порядок big-endian.

## 2. Заголовок и концевик кадра

Каждый кадр начинается с одних и тех же четырёх байт и завершается CRC-16, вычисленным по всем предшествующим байтам.

| Смещение | Размер | Поле |
| ---: | ---: | --- |
| 0 | 2 | Сигнатура `0x56 0x51` (`VQ`) |
| 2 | 1 | Версия формата, значение `1` |
| 3 | 1 | Тип: `1` — манифест, `2` — данные |

CRC-16/CCITT-FALSE: полином `0x1021`, начальное значение `0xFFFF`, без отражения, xor-out `0`. Контрольное значение: `crc16("123456789") = 0x29B1`.

### 2.1 Кадр данных

| Смещение | Размер | Поле |
| ---: | ---: | --- |
| 4 | 6 | Идентификатор файла |
| 10 | 2 | Номер сегмента |
| 12 | 4 | Индекс символа (`uint32`) |
| 16 | `blockLen` | Полезная нагрузка символа |
| 16 + `blockLen` | 2 | CRC-16 |

`blockLen = frameBytes - 18`. Каждый кадр данных одного потока MUST использовать `blockLen`, записанный в манифесте.

### 2.2 Кадр манифеста

| Смещение | Размер | Поле |
| ---: | ---: | --- |
| 4 | 6 | Идентификатор файла |
| 10 | 1 | Номер части, начало отсчёта 0 |
| 11 | 1 | Число частей, диапазон 1..255, при условии `part < parts` |
| 12 | `n` | Срез тела манифеста |
| 12 + `n` | 2 | CRC-16 |

Тело разбивается на срезы длины `frameBytes - 14`. Заключительный срез может быть короче.

### 2.3 Классификация на приёмнике

1. Вход не начинается с `56 51` либо его длина меньше 4 байт: вердикт **foreign**. Вход игнорируется. Камера наблюдает каждый символ в поле зрения.
2. Байт версии отличается от версии приёмника: вердикт **unsupported-version**. Приёмник сообщает о необходимости обновления приложения.
3. Длина ниже минимума для данного типа либо CRC не совпадает: вердикт **corrupt**. Вход отбрасывается, что эквивалентно неуспешному чтению.
4. В остальных случаях вердикт — **ok**.

Приёмник отслеживает ровно один идентификатор файла в каждый момент времени. После принятия манифеста кадры с иным идентификатором файла игнорируются.

## 3. Тело манифеста

| Размер | Поле |
| ---: | --- |
| 1 | Версия манифеста (`1`) |
| 1 | Флаги (в версии 1 MUST быть равны `0`) |
| 2 | `blockLen` |
| 2 | `K`: число блоков наибольшего сегмента, диапазон 1..4096 |
| 4 | `segmentCount` |
| 4 + 4 | `fileSize`, старшее слово, затем младшее слово |
| 1 | Длина таблицы степеней `L` |
| 2 · `L` | Таблица степеней, каждая запись — `uint16` |
| 1 + `n` | Имя файла, UTF-8, `n` ≤ 255 |
| 1 + `n` | Медиатип, UTF-8, `n` ≤ 255 |
| 32 · `segmentCount` | SHA-256 реальных байт каждого сегмента |

**Идентификатор файла** — первые 6 байт `SHA-256(тело)`. Приёмник MUST собрать тело, заново вычислить идентификатор и отбросить манифест при расхождении значений. Данная конструкция связывает имя, размер, хэши сегментов и таблицу степеней с идентификатором, который несёт каждый кадр.

До использования манифеста для определения размера буфера приёмник MUST отклонить манифест, если не выполнено хотя бы одно из условий: `blockLen` ≥ 16; `1 ≤ K ≤ 4096`; `1 ≤ fileSize` и `fileSize` не превосходит предел приёмника (эталонный предел — 256 МиБ); `segmentCount = ceil(ceil(fileSize / blockLen) / K)`; флаги равны `0`; таблица степеней корректна (раздел 4.3); обе строки являются корректным UTF-8; тело завершается непосредственно после списка хэшей. Приёмник MUST NOT толковать имя файла как путь файловой системы до очистки имени.

Отправитель повторяет манифест в ходе потока (раздел 6). Приёмнику требуются все части одного манифеста, прежде чем кадр данных может быть потреблён.

### 3.1 Сегментация

`totalBlocks = ceil(fileSize / blockLen)`. Файл разбивается на блоки длины `blockLen` байт. Заключительный блок дополняется нулями исключительно для кодирования. Блоки образуют `segmentCount` последовательных сегментов. Пусть `base = floor(totalBlocks / segmentCount)` и `extra = totalBlocks mod segmentCount`. Сегмент `s` содержит `base + 1` блоков при `s < extra` и `base` блоков в противном случае. Длины сегментов различаются не более чем на один блок. Сегмент `s` начинается с блока `s · base + min(s, extra)`. Хэш сегмента покрывает реальные байты файла. Дополнение заключительного блока в хэш не включается.

Отправитель выбирает `segmentCount = ceil(totalBlocks / kMax)` и `K = ceil(totalBlocks / segmentCount)`. *Пояснение: допустим любой `segmentCount`, удовлетворяющий приведённому выше правилу проверки.*

## 4. Символы

### 4.1 Генератор

Арифметика является исключительно целочисленной. Произведения сворачиваются как `uint32` (`Math.imul`).

```
fmix32(h):  h ^= h >>> 16; h *= 0x85ebca6b; h ^= h >>> 13; h *= 0xc2b2ae35; h ^= h >>> 16
Rng(seed):  state = seed;  next(): state += 0x9e3779b9; return fmix32(state)
symbolSeed(id32, segment, index):
    h = fmix32(id32 ^ 0x5651445f)
    h = fmix32(h ^ ((segment + 1) * 0x9e3779b1))
    h = fmix32(h ^ ((index + 1) * 0x85ebca77))
```

`id32` — первые 4 байта идентификатора файла, интерпретируемые как big-endian `uint32`. Тестовые векторы приведены в разделе 8.

### 4.2 Построение символа

Для сегмента, содержащего `k` блоков (размер данного сегмента, не `K`), таблицы `T` и символа `(segment, index)`:

```
rng    = Rng(symbolSeed(id32, segment, index))
r16    = rng.next() >>> 16
degree = min(k, 1 + наименьший i, при котором r16 <= T[i])
set    = []
while |set| < degree:
    b = rng.next() mod k
    if b not in set: append b
```

Полезная нагрузка есть побитовое XOR блоков из `set`. Блоки за пределами реальных данных трактуются как нули. Декодер восстанавливает `set` исключительно из `(segment, index)`. Кадр поэтому не содержит списка соседей.

### 4.3 Таблица степеней

`T` содержит `L` записей при `1 ≤ L ≤ K`. Последовательность неубывающая, `T[L - 1] = 0xFFFF`. `T[i]` — наибольшая 16-битная выборка, которая ещё отображается в степень `i + 1`. Приёмники читают таблицу и не вычисляют её заново. Способ построения, применяемый отправителем, не ограничен, поскольку таблица переносится в манифесте и значения с плавающей точкой в приёмник не поступают.

*Пояснение. Эталонный отправитель:*

- При `K ≤ 64`: биномиальное распределение `Binomial(K, 1/2)` при условии степени не менее 1, `P(d) = C(K, d) / (2^K - 1)`.
- В остальных случаях: распределение robust soliton (Luby, 2002) с параметрами `c = 0.05` и `δ = 0.01`, усечённое на степени 128 и хранимое в виде 16-битных накопленных порогов.

## 5. Декодирование

*Пояснение, за исключением проверки хэша, которая является нормативной.*

Сегмент декодируется из любого множества символов, уравнения которого имеют полный ранг над GF(2). Результат является функцией множества индексов. Он не зависит от порядка поступления и от повторов. Эталонный декодер применяет распространение уверенности по мере поступления символов и завершает неразрешённый остаток методом исключения Гаусса над GF(2). Проход только по структуре, без полезных нагрузок, определяет, подлежит ли выполнению полное декодирование.

После декодирования приёмник MUST вычислить SHA-256 по реальным байтам и сравнить дайджест с манифестом. При несовпадении приёмник MUST отбросить всё состояние, удерживаемое для данного сегмента, и начать сбор сегмента заново. Символ может нести корректный CRC и некорректное содержимое. Измеренные накладные расходы эталонной таблицы составляют приблизительно 1,01–1,04 от `K` в среднем при `K ≥ 200`. 99-й перцентиль ниже 1,1 от `K` (`bench/overhead.js`).

## 6. Расписание передачи

*Пояснение. Настоящий раздел не входит в формат на проводе. Приёмники MUST NOT зависеть от него.*

- Поток не имеет заключительного кадра. Эталонный отправитель сначала излучает полный манифест, затем одну часть манифеста после каждых 90 кадров данных.
- Кадры данных излучаются кругами. Круг 0 поставляет каждому сегменту `1.06·K + 2` новых символов. Последующие круги поставляют `min(1, 0.06·2^(lap-1))·K + 2`, чередуя сегменты по одному символу. Индексы символов внутри сеанса не повторяются. Случайное начальное смещение исключает повтор индексов, уже удерживаемых возобновляющим приёмником, со стороны перезапущенного отправителя.
- Память отправителя удерживает только сегменты текущего окна. Окно по умолчанию — 32 МиБ.
- Повторная передача тех же байт даёт тот же манифест и тот же идентификатор файла. Прерванный приёмник поэтому может возобновить приём в отношении последующего сеанса.

## 7. Соображения безопасности

Версия 1 обеспечивает целостность в отношении порчи посредством SHA-256 на каждый сегмент и манифеста, связанного с идентификатором файла. Спецификация не выполняет аутентификацию дисплея. Сторона, способная предъявить поток QR, способна предъявить произвольный файл. Шифрование не определено. Наблюдение дисплея даёт файл. Приёмники MUST трактовать имя файла и медиатип как недоверенные, MUST ограничивать каждое выделение памяти проверенным манифестом и MUST NOT исполнять принятый файл.
